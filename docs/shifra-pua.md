# שפרה ופועה

## הפעלה

- עמוד ציבורי: `/shifra-pua`; מסך ניהול: `/admin/shifra-pua` (מופיע בניווט האדמין).
- אין תלות חדשה או משתנה סביבה חדש. משתמשים בחיבור MongoDB, בהגדרות API ובאימות האדמין הקיימים.
- יש לבנות ולפרוס גם את השרת וגם את הלקוח. בפיתוח: `npm run dev --prefix server` ו־`npm run dev --prefix client`.
- בהפעלת השרת נוצרים האוסף והאינדקסים של `ShifraPuaRegistration`. נדרשת למשתמש MongoDB הקיים הרשאת יצירת אינדקסים. האינדקס הייחודי נוצר לפני שהשרת מתחיל לקבל בקשות.
- אין שליחת הודעות או התראות אוטומטיות עם פרטי יולדות. כל כפתורי ההתנדבות בעמוד פותחים WhatsApp לתמר במספר **0542193770** (`https://wa.me/972542193770`), עם ההודעה המוכנה: ״היי תמר, אשמח להצטרף להתנדבות בשפרה ופועה ולעזור בהכנת ארוחות הבוקר ליולדות ביפו ❤️״. מספר הקשר הכללי והכפתור הצף באתר נשארים ללא שינוי.

## תהליך העבודה

1. הרשמה חדשה מקבלת סטטוס ״חדשה״ ומועד חלוקה התחלתי ביום רביעי הקרוב, כולל היום אם היום רביעי, לפי שעון ישראל.
2. לאחר תיאום טלפוני בוחרים ״תואמה״ ואת תאריך החלוקה הרצוי. ניתן לבחור ידנית גם יום אחר.
3. בתצוגת ״הכנות וחלוקה״ בוחרים תאריך: המונה סופר את כל ההרשמות שתואמו לאותו תאריך, והכרטיסים מציגים כתובות, פרטי קשר ורגישויות. חיפוש מצמצם את הכרטיסים בלבד. כשיש יותר מ־30 כרטיסים, עוברים בין העמודים כדי לראות את כל הכתובות.
4. לאחר המסירה לוחצים ״סימון: הארוחה נמסרה״. הסימון מתעד מסירה בהיסטוריה, עם התאריך והכתובת בזמן הסימון.
5. הרשמה כפולה עם אותו טלפון מנורמל ואותו תאריך לידה לא יוצרת רשומה חדשה ולא משנה את הפרטים הקיימים. התגובה הציבורית זהה לתגובה על הרשמה חדשה, כדי לא לחשוף אם היולדת רשומה.
6. לידה אחרת עם אותו טלפון יוצרת הרשמה נפרדת. מסירות מלידות קודמות נספרות ומסומנות בכרטיס, ואפשר לצפות בהיסטוריית הלידות והארוחות.
7. לטיפול חריג אפשר לתקן פרטים והערות צוות ב״תיאום ועדכון״ או לפתוח מחדש הרשמה באמצעות שינוי סטטוס. המסירות שכבר תועדו נשמרות; מעבר נוסף ל״הארוחה נמסרה״ מתעד ארוחה נוספת. אין לשנות תאריך לידה ישן כדי לרשום לידה חדשה - יש להשתמש בטופס הציבורי.
8. עדכון שמתנגש בעדכון ממכשיר אחר נחסם. יש לרענן ולטעון את הרשומה העדכנית לפני שמירה נוספת.

## אבטחה

- ה־API הציבורי מקבל רק שדות הרשמה מורשים ומחזיר `{ success: true }`, ללא פרטים אישיים. ולידציה, הגבלת קצב ואינדקס ייחודי חלים בשרת.
- רשימות, חיפוש, היסטוריה ושינויים מוגנים באמצעות `requireAdmin`; שינויים מוגנים גם באמצעות `requireSecureAdminMutation`.
- תגובות ה־API כוללות `no-store`; מידע אינו נשמר באחסון הדפדפן ולא נשלח ביוזמת הרכיבים לאנליטיקה או לספקי הודעות. שגיאות השרת אינן מדפיסות את תוכן הרשומות.
- סינון תאריכי הרשמה מתייחס ליום המקומי בישראל, כולל שינויי שעון קיץ.
- פרטי ההרשמות נשמרים באותו מסד נתונים ובאותם מנגנוני גיבוי והרשאות של האתר. אין מערכת זהויות חדשה או שירות חיצוני נוסף.

## בדיקות

```sh
npm run build --prefix client
npm test --prefix client
npm test --prefix server
```

בדיקות השרת החדשות נמצאות ב־`server/src/tests/shifraPua.test.ts`. בדיקת מסד הנתונים דורשת מסד מקומי זמני ומבודד, ואינה קוראת את `MONGO_URI` של האתר. היא מוחקת בסיום רק את מסד הבדיקה שבכתובת שהוגדרה:

```sh
npm run build --prefix server
SHIFRA_TEST_MONGO_URI=mongodb://127.0.0.1:27029/shifra_qa_local node --test server/dist/tests/shifraPua.test.js
```

שם מסד הבדיקה חייב להתחיל ב־`shifra_qa_`, בשרת המקומי ובפורט 27029. ללא המשתנה, בדיקת מסד הנתונים מדולגת ובדיקות הוולידציה וההרשאות רצות כרגיל.

## תמונת הפתיח

תמונת המחשה שנוצרה בבינה מלאכותית נשמרת ב־`client/public/shifra-pua/breakfast-hero.webp`, עם גרסה ברוחב 768 פיקסלים. בהמשך אפשר להחליף את שני הקבצים בצילום אמיתי של הפעילות; אם יחס הממדים משתנה יש לעדכן גם את מידות התמונה ברכיב.

## קניות והכנות שבועיות

- בלשונית ״קניות והכנות״ בוחרים יום רביעי (ברירת המחדל לפי שעון ישראל). בחירת תאריך קודם מציגה את רשימות אותו שבוע.
- רשימות הקניות והמשימות נשמרות באוסף `ShifraPuaWeek`, עם אינדקס ייחודי לתאריך שנוצר באתחול השרת. אין צורך במשתנה סביבה חדש.
- מוסיפים שם, ואז אפשר לערוך כמות ויחידה חופשיות. עריכת שדה נשמרת ביציאה ממנו; סימון, הוספה ומחיקה נשמרים מיד. מוצגת הודעת אישור רק אחרי תשובת השרת.
- בזמן שמירה הרשימות נעולות לרגע. בכשל השינוי נשאר מוצג ואפשר לנסות שוב. בהתנגשות בין משתמשות השרת מחזיר 409 ואין דריסה; יש לטעון מחדש ולהחיל שוב את השינוי על המידע העדכני. טעינה מחדש לאחר כשל מבקשת אישור לאובדן הטיוטה.
- מספר הארוחות סופר הרשמות שתואמו לתאריך המדויק ומתעדכן בטעינה מחדש. הוא אינו משנה את הרשימות. אפשר להזין כמויות ידנית או ליצור רשימות מתפריט, דרך תצוגה מקדימה ואישור מפורש.
- כל רשימה מוגבלת ל־300 פריטים. הרשאות האדמין, הגנת מקור הבקשה וכותרות no-store חלות גם על API השבועות.
- בדיקת מסד הנתונים ב־`shifraPua.test.ts` מכסה יצירה, עריכה, מחיקה, סימונים, טעינה חוזרת, בידוד שבועות, שמירה מקבילה ויצירה מקבילה של אותו שבוע.


## מאגר מנות ותכנון אוטומטי

- המאגר הראשוני המאושר נמצא ב־`server/src/services/shifraPlanning/catalog.ts`: 8 עיקריות, 6 סלטים, 4 רטבים, 4 סוגי לחם, 6 גבינות וממרחים ו־6 קינוחים. המנות ניתנות להוספה, עריכה ומחיקה דרך האדמין, כולל מצרכים למנה, יחידות, הוראות ומשימות. הכמויות הראשוניות הן **הצעה**, ומוצגות לעיון ולאישור לפני יצירת רשימות.
- ברירות המחדל הן נתונים לקריאה מהקוד. אין פעולת seed ואין migration המשנה שבועות קיימים. שינויים במאגר נשמרים ב־`ShifraPuaRecipe`, כולל סימון הסרה למנות ברירת מחדל כדי שלא יחזרו לאחר הפעלה מחדש. יצירה/עריכה/מחיקה משתמשות בגרסה למניעת דריסה בין עורכות.
- בכל כניסה מוצעת הרכבה קבועה לאותו תאריך, המעדיפה הכנה בכמות, קינוחים קנויים ורוטב תואם לסלט. התפריטים שאושרו בשמונה השבועות הקודמים הזמינים מקבלים משקל המפחית חזרות, בעיקר בשבוע הסמוך. ההצעה אינה נכתבת למסד עד אישור; תפריט שכבר אושר מוצג כפי שנשמר.
- החלפת סלט בוחרת גם רוטב מתאים מתוך ההגדרות במאגר; אפשר להחליפו ידנית. עריכת מנה במאגר אינה משנה אוטומטית תפריט מאושר. אם עורכים רכיב שנבחר, הגרסה החדשה נבחרת כטיוטה בלבד ותדרוש בדיקה ואישור להחלה.
- ״אישור התפריט · בדיקת הרשימות״ מציג את כל התוספות, העדכונים וההסרות ואת הרשימות המלאות לאחר ההחלה. רק לחיצה על כפתור האישור בתוך התצוגה המקדימה שומרת את התפריט והרשימות יחד, בעדכון אטומי אחד של השבוע.
- חישוב המצרכים מסכם כמויות למנה ומכפיל במספר ההרשמות שתואמו לתאריך. שמות זהים מאוחדים לאחר נרמול רווחים; ק״ג מומרים לגרם וליטר למ״ל. יחידות ופרוסות מעוגלות למעלה לאחר הסיכום. שמות שונים או יחידות שאינן ניתנות להמרה אינם מאוחדים בניחוש. נכללים חומרי אריזה וברכות ומשימת הרכבת מספר המארזים המחושב.
- שבוע ישן ללא נתוני יצירה אוטומטית נחשב ידני במלואו. כל שורה ידנית נשמרת; אם קיים פריט ידני עם אותו שם ויחידה תואמת, המערכת נמנעת מיצירת כפילות ומציגה את הכמות המחושבת לבדיקה ידנית.
- עדכון תפריט או ספירה מחליף רק שורות אוטומטיות שלא סומנו ולא נערכו. פריטים שסומנו, שונו או נמחקו ידנית נשמרים כהחלטות משתמשת גם בעדכונים הבאים. פערים בין הכמות המחושבת לבין פריט מוגן מוצגים לבדיקה, כולל פריט שנקנה ואינו נדרש עוד. אין השלמה אוטומטית שעלולה לגרום לרכישה כפולה.
- התצוגה המקדימה קשורה לתוכן המתכונים, לגרסת השבוע, לתוכן הרשימות ולמספר הארוחות בזמן החישוב. השרת מחשב שוב לפני אישור ומחזיר 409 אם ההצעה התיישנה. שני אישורים על אותה גרסה אינם יכולים לדרוס זה את זה. ספירת ארוחות חדשה נטענת בכניסה או ב״טעינה מחדש״; עצם שינוי ההרשמות אינו משנה רשימה.
- כל אישור שומר snapshot של המתכונים, הספירה, המועד והעורכת בתוך `menuHistory` של השבוע. ״תפריטים מוצלחים״ שומר snapshot נוסף ב־`ShifraPuaSavedMenu`; שימוש חוזר מחשב מחדש לפי השבוע החדש ודורש אישור. מחיקת מתכון או מועדף אינה משנה את ההיסטוריה.
- ה־API החדש מוגן באותן הרשאות ומנגנוני מקור בקשה של שפרה ופועה. אין גישה ציבורית למאגר או לתכנון ואין תלות או משתנה סביבה חדש.

### בדיקות התכנון

`server/src/tests/shifraPlanning.test.ts` כולל חישובים, התאמת רטבים, גיוון, המרות, עיגול, כמות אפס, הגנה על שינויים ידניים ומחיקות, CRUD, שמירה וטעינה חוזרת, תפריטים מועדפים, ספירה שהתיישנה ואישורים מתחרים. בדיקות MongoDB משתמשות במסד זמני עם הסיומת `_planning`, בנפרד מבדיקות ההרשמות.

```sh
npm test --prefix server
npm test --prefix client
# מפעיל ומנקה מסדי MongoDB מקומיים זמניים בלבד; דורש mongod זמין:
npm run test:db --prefix server
```

בדיקות הלקוח ב־`test-registration-resilience.mjs` מפעילות את רכיבי React עם שירות מדומה כדי לוודא שאין שמירה לפני אישור, שאין אישור כפול, שכשל שומר את ההצעה ושהחלפת סלט מתאימה רוטב ומבטלת הצעה קודמת. בדיקה חזותית מקומית בתצוגת טלפון בוצעה עם נתוני דמה בלבד: אישור, סימון קנייה, רענון, שמירת תפריט מוצלח, עריכת מתכון והחלפת עיקרית תוך שמירת הסימון. צילומי הבדיקה נשמרו ב־`/tmp` בלבד.
