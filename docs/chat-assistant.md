# עוזר שאלות נפוצות

ברירת המחדל היא `CHAT_PROVIDER=local`: התאמה דטרמיניסטית לפי ביטויים, ללא רשת, ללא הבנה סמנטית וללא שימוש בהיסטוריה להסקת כוונה. העובדות והיעדים נמצאים ב־`server/src/config/assistantKnowledge.ts`. בחירה מפורשת בספק OpenAI מפעילה את Responses API המתואר בהמשך; Gemini מושבת. בבדיקה הנוכחית אין להפעיל ספק חיצוני.

בקשות הלקוח משתמשות ב־fetch עם `credentials: omit`, ללא הרשאות מנהל. רק קלט תקין שעבר מגבלת IP נספר במכסה היומית. המגבלה היא חלון קבוע של 15 פניות ב־60 שניות ל־IP; אינה חלון נע. `ASSISTANT_DAILY_LIMIT` נקרא בזמן בקשה: מספר שלם בין 1 ל־10000, וברירת מחדל 500. המכסה סופרת בקשות שהתקבלו לעיבוד, גם אם העיבוד נכשל.

כל המונים בזיכרון של תהליך יחיד בלבד. הפעלה מחדש מאפסת אותם; לכל מופע מכסה עצמאית. האיפוס היומי בחצות UTC ולא לפי שעון ישראל. נדרשת תצורת proxy מהימנה לזיהוי IP. אין כאן הבטחת תקציב כוללת בפריסה עם כמה מופעים.

429 מחזיר `IP_RATE_LIMIT` או `DAILY_QUOTA`; קלט שגוי מחזיר `INVALID_MESSAGE` או `INVALID_HISTORY`. לא נרשמים תוכן שיחה או שגיאות חופשיות ללוגים.

החלון הוא דיאלוג שאינו מודאלי; העמוד נשאר זמין. במכירה ובמידע להורי המעון נשמר מקום לסרגל הפעולות בתחתית. יש לבדוק חזותית גם הגדלת טקסט ומקלדת במכשירים לפני פריסה.

## חיבור OpenAI (עודכן 22.09.2026)

`CHAT_PROVIDER=openai` מפעיל בשרת בלבד את `gpt-5-mini` דרך `POST https://api.openai.com/v1/responses`. `local` או ערך שאינו נתמך משאירים את המנוע המקומי. `OPENAI_MODEL` הישן אינו בשימוש: המודל קבוע כדי למנוע החלפה לא מאומתת. Gemini אינו מופעל.

ב־Railway יש להגדיר בשירות השרת בלבד:

- `CHAT_PROVIDER=openai` להפעלה, או `local` לחזרה מיידית למצב המקומי.
- `OPENAI_API_KEY` - מפתח של פרויקט OpenAI עם גישה למודל ותקציב זמין. אין להגדיר משתנה `VITE_` למפתח.
- `ASSISTANT_DAILY_LIMIT` - אופציונלי; מומלץ להתחיל במכסה נמוכה. ברירת המחדל הקיימת היא 500.

אין צורך בתלות SDK נוספת. `fetch` של Node שולח רק הנחיות, עובדות ציבוריות הנגזרות מ־`assistantKnowledge.ts`, עד שש הודעות קודמות (עד 1,000 תווים כל אחת), והשאלה הנוכחית (עד 500 תווים). ההיסטוריה כוללת רק הודעות קודמות; אין להסיר הודעות לפי שוויון טקסט. הלקוח הקיים כבר מפריד את ההודעה הנוכחית. אין העברת cookies, כותרות האתר, הרשאות מנהל, מידע ממסד נתונים או מטא־דאטה מהבקשה. הרשאת Bearer היחידה היא מפתח OpenAI של השרת. בשני הצדדים נשמר `credentials: "omit"`; הפניות HTTP חסומות.

המודל מפרש הקשר בשפה טבעית ובוחר עד שלוש עובדות לפי מזהים בפלט מובנה. אין שימוש במילות מפתח לפתרון שאלות המשך במסלול OpenAI. השרת מציג משפטים שנוצרו אך ורק מהמאגר, ולא מציג טקסט חופשי שהמודל יצר. כך אין אפשרות להוסיף כתובת, מחיר או פסיקה חדשה בפלט. סוגי unknown/partial מוסיפים הפניה לוואטסאפ; halachic מחזיר הודעת חוסר סמכות והפניה לרב; blocked אינו חושף הנחיות. עדיין תיתכן בחירה שגויה של עובדה מאושרת או סיווג כוונה שגוי, ולכן נדרשת הערכת איכות אמיתית לפני הפעלה רחבה. המענה מוגבל ומנוסח מתבניות מאושרות כדי לשמור על אמינות.

עלויות: בקשה אחת ללא ניסיונות חוזרים, `reasoning.effort=minimal`, `text.verbosity=low`, תקרת `max_output_tokens=600` (כוללת טוקני reasoning), עד שלוש עובדות בתשובה, timeout של 12 שניות. נשמרו מגבלות הקצב והמכסה היומית. תקרת פלט או timeout עשויים לגרום לחזרה למקומי; גם בקשה כזו עלולה להיות מחויבת אצל הספק. `store=false` מונע שמירת מצב Responses; אינו הבטחה למדיניות אפס שמירת נתונים אצל הספק.

`getAssistantUsage()` מספק צילום מונים מספריים מצטברים בזיכרון התהליך: responses, inputTokens, outputTokens, totalTokens. אין לוג שיחה, מזהה משתמש או נתיב ציבורי למונים. המונים מודדים רק usage תקין שהתקבל; הם אינם מערכת billing או מדידה מלאה של בקשות שנותקו. בכשל נרשמת הודעה קבועה בלבד, ללא גוף השגיאה, סטאק, מפתח, כותרות או תוכן שיחה. שגיאה, refusal, JSON פגום, פלט לא גמור או מזהה עובדה לא מאושר עוברים למנוע המקומי הקיים, ללא חיווי ספק בממשק. למנוע המקומי אין הבנת הקשר סמנטית.

אימות התיעוד הרשמי לפני המימוש:

- https://developers.openai.com/api/docs/models/gpt-5-mini
- https://developers.openai.com/api/docs/guides/migrate-to-responses
- https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5
- https://developers.openai.com/api/docs/guides/structured-outputs

בדיקות ללא API אמיתי: `npm run build` בתיקיית server, ואז `node --test dist/tests/chatAssistant.test.js dist/tests/chatOpenAI.test.js`; בתיקיית client: `node scripts/test-chat-assistant.mjs`. בדיקות OpenAI מחליפות fetch וחוסמות גם axios ויצירת חיבורי רשת. הן בודקות חוזה בקשה, הקשר, פרטיות, מכסות, פלט ו־fallback, ולא מוכיחות שהמודל עצמו מסווג נכון. לבניית הלקוח בלי קריאת קובצי סביבה: `tsc -b` ולאחריו `node --input-type=module -e 'import { build } from "vite"; await build({ envDir: false });'`.

לפני production: להגדיר סודות ב־Railway, לוודא גישת החשבון למודל ותקציב, לבדוק proxy ומספר מופעים מול המכסה בזיכרון, לבצע בסביבת בדיקה הערכת שיחות אמיתית באישור נפרד (צהלון → טלפון/רב, מעבר לקמפוס, מחיר/ערב/ילדים, הלכה והזרקת הוראות), ואז להפעיל בהדרגה עם מכסה נמוכה. בזמן המימוש לא נקראו קובצי .env ולא בוצעה קריאת API אמיתית.

## מדידת שימוש בצ׳אט

משתמשים בתשתית GA4/gtag הקיימת (`G-N3TDW4B08C`), ללא תלויות נוספות. `chatAnalytics.ts` מרכז את האירועים, מסנן ערכים בריצה, ובולע כשל סינכרוני או Promise שנדחה. אין המתנה לאנליטיקה, שליחה חלופית, אחסון מקומי או מזהה חדש. אין שינוי להגדרות consent; לא נמצאה מערכת consent באתר. החרגת `/daycare/onboarding/` נשמרת גם בניווט לקוח.

| אירוע | פרמטרים מותאמים אישית |
| --- | --- |
| `chat_open` | אין; בכל פתיחה |
| `chat_conversation_started` | אין; בשליחה הראשונה בלבד עד איפוס או הסרת הרכיב |
| `chat_message_sent` | אין; לכל שליחה שהתקבלה בממשק, כולל ניסיונות שנכשלו |
| `chat_action_clicked` | `action_type`: רק `whatsapp`, `gallery`, `daycare`, `donation`, `home`, `contact`, `other` |
| `chat_no_info` | אין; פעם לתשובה עם נוסח חוסר מידע קיים, כולל תשובה חלקית |
| `chat_error` | `error_code`: רק `frontend_fetch_failed`, `frontend_response_not_ok`, `frontend_response_parse_failed`, `rate_limited`, `daily_limit`, `request_failed` |
| `chat_reset` | אין; בכל איפוס |

סגירה ופתיחה אינן מתחילות שיחה חדשה. ביטול בקשה באיפוס/הסרת הרכיב ותשובה ישנה שנזרקה אינם נספרים כשגיאה או כחוסר מידע. כשל HTTP נספר פעם אחת גם אם פענוח גוף השגיאה נכשל. סיווג חוסר מידע נעשה בזיכרון הלקוח לפי התבנית הקיימת `אין לי כרגע מידע ... אפשר לברר איתנו בוואטסאפ.`; יש לעדכן אותו אם נוסחי השרת משתנים. לא שונתה לוגיקת השרת לשם המדידה.

האירועים המותאמים אינם כוללים תוכן, אורך טקסט, היסטוריה, מזהי עובדות, כתובות יעד, IP, מידע אישי, מפתחות או כותרות. זה אינו מבטל את איסוף המטא־דאטה והעוגיות הרגיל של תשתית GA4 הקיימת: GA מקבל כתובת IP ברמת התעבורה ומשליך אותה לפני השמירה לפי תיעוד Google. אין כאן הבטחה לאנונימיות מוחלטת של GA4 או לשינוי הגדרות Enhanced Measurement בנכס.

לאחר פריסה, בדוח Events אפשר לסנן שמות המתחילים ב־`chat_` ולמדוד Event count. ב־Admin → Custom definitions יש ליצור שני ממדים בהיקף Event: `action_type` ו־`error_code`. ב־Explore מציגים Event name ו־Event count עם הממדים הללו לפילוח פעולות ושגיאות. הערכים עשויים להופיע בדוחות לאחר 24–48 שעות. לא בוצעו שינויים בחשבון Analytics או שליחת אירועי בדיקה אמיתיים.

מדדים באותו טווח תאריכים (ניתן לחשב מהספירות בדוח מיוצא או בלוח דיווח):

- פתיחות, שיחות והודעות: ספירות האירועים המתאימים.
- ממוצע הודעות לשיחה: `chat_message_sent / chat_conversation_started`.
- שיעור חוסר מידע מכל השליחות: `chat_no_info / chat_message_sent`.
- שיעור שגיאות מכל השליחות: `chat_error / chat_message_sent`.
- לחיצות WhatsApp ופעולות אחרות: `chat_action_clicked` בפילוח `action_type`.

היחסים הם מדדים מצרפיים, עם בדיקת מכנה שאינו אפס; אינם מעקב אחר שיחה בודדת. שיחות שחוצות טווח תאריכים, חסימת אנליטיקה וביטולים עשויים להשפיע עליהם. אין להציג את שיעור חוסר המידע מתוך שליחות כשיעור מתוך תשובות שהושלמו.

מקורות: [אירועים מותאמים](https://support.google.com/analytics/answer/12229021?hl=en), [ממדים מותאמים](https://support.google.com/analytics/answer/14240153?hl=en), [איסוף אזורי ו־IP](https://support.google.com/analytics/answer/11598602?hl=en).
